      Recording 1, the other side

      The feature works. Five things are missing.

      • It graded itselfThe same agent wrote the code and the tests. No one independent checked the work.
      • No standardIt followed whatever Angular style it guessed. Your team's rules were not in the session.
      • No requirementThe model decided what done meant. There was no list of criteria to check against.
      • No recordIt left no report and no status entry. The next person has nothing to read.
      • No memoryEverything it learned about this code is gone when the session ends.

      The run was also cheap and correct. On one small task that is a fair trade. Across a whole backlog, these five gaps add up.

      Say this plainly. The run was cheap and correct. The problem is not one run. The problem is fifty runs by six developers with no shared standard and no audit record. That is how a codebase drifts.

      The thesis

      Your job is supervision.

      The model writes the code. You own four things the model cannot decide for itself.

      01Context

      Context is what the tool can read. Your rules, your patterns, and your API contract live in files in the repo, not in a prompt.

      02Goals

      A goal is a requirement with criteria a machine can check. It names exact labels, exact counts, and exact responses.

      03Plans

      A plan is one requirement per run. You order the requirements by dependency, and you split anything bigger than one run.

      04Gates

      A gate is a check that must pass before the work counts. The gates are the build, the tests, the coverage, and an independent audit.

      This is the one slide to remember. The four words are context, goals, plans, and gates. Every Tool-Kitt skill in this talk serves one of the four.

      The tool

      Tool-Kitt is a set of Claude Code plugins.

      Claude Code runs the loop, the tools, and the permissions. Tool-Kitt adds the rules, the roles, and the checks. Nothing in Tool-Kitt re-teaches the model what it already knows.

      PluginWhat it addsWhich of the four
      kitt-coreThe MCP server, the doctor, project setup, requirement drafting, handoffs, and the learnings fileContext and goals
      kitt-crewThe four agents, which are the scout, the coder, the tester, and the auditor. They handle one requirement per run.Plans and gates
      kitt-angularAngular patterns, an architecture advisor, and a reviewer that rejects React habitsContext
      kitt-python, kitt-auditors, kitt-metaPython services, skill auditors, and tools for writing your own skillsContext
      Be precise here. Tool-Kitt is not the harness. Claude Code is the harness. Tool-Kitt is a method layer on top. That is why the same files work from Gemini CLI and Copilot CLI.

      Install

      Three commands install it.

      • /plugin marketplace add jrwhip/tool-kittThis registers the marketplace. The marketplace is a git repo, so there is nothing else to host.
      • /plugin install kitt-core@kitt-marketplaceInstall this one first. It carries the MCP server that every other pack calls.
      • /plugin install kitt-crew@kitt-marketplaceThen install the crew. Angular projects also install kitt-angular.

      There is one prerequisite. The server runs through uv, a static binary that provides its own Python. It needs no admin rights.

      Plugins can be turned on per project, so an Angular repo carries only the packs it needs. Mention uv once and move on.

            Context

            Your standards become a file the coder must read.

            specs/coder-spec.mdexcerpt
            ## Architecture Patterns

### Standalone components only
No `NgModule`. Components import their own dependencies.

### Signals for reactive state
- Component state: `signal()`, `computed()`, `linkedSignal()`.
- Async: `resource()` / `httpResource()`. `toSignal()` for RxJS interop.
- Do NOT use `BehaviorSubject` for component-local state.

### OnPush change detection
Every new component declares `changeDetection: OnPush`.

## API Consumption
1. Never hand-write HTTP services or request/response types.
2. Never hand-edit the generated client. Missing endpoint? STOP and flag it.

## Anti-Patterns (auditor surfaces these as BLOCKERs)
- `@Component` without OnPush in new code.
- `subscribe()` inside a component body without a teardown.
- Reactive forms for new feature work when signal forms exist.
            • Why a fileTraining data is full of React habits written in Angular syntax. A spec file in the repo overrides the training data on every run.
            • Who reads itThe coder reads it before writing code. The auditor reads it to decide BLOCKED or UNBLOCKED. One file serves two jobs.
            • Who maintains itYou maintain it by default. If you turn on spec_writes, the coder may propose changes when a new pattern earns a place.
            This is the context part of the thesis. The spec is a plain markdown file. It ships pre-filled for Angular, FastAPI, and Spring Boot. You edit it like code, and you review changes to it like code.

            Goals

            A requirement is a list of checks a machine can run.

            requirements/REQ-ML-1.mdexcerpt
            ---
id: REQ-ML-1
title: Filter the mission list by status
status: pending
---
## Requirement
Adds a status filter with three choices (All, Open, Done) and a
count line. Does not add sorting, search, persistence, or any
change to the Mission Log API.

## Acceptance criteria
1. One filter control with exactly three options labelled
   "All", "Open", and "Done". "All" is selected on first render.
4. A count line reads "Showing N of M missions".
   3 returned, 2 open, "Open" selected: "Showing 2 of 3 missions".
5. No match: the text "No missions match this filter." and
   "Showing 0 of M missions".
7. Changing the filter sends no new request to the API.
8. `ng test` passes with zero failures, including pre-existing tests.
10. No file under `src/api/` changes.
            • The barIf two honest reviewers could disagree about whether a criterion is met, rewrite the criterion. Use exact labels, exact text, and exact counts.
            • No implementationA requirement names no files, no components, and no libraries. A criterion that restates the code certifies anything.
            • Where it livesA requirement is a markdown file in the requirements/ folder or a Jira issue. The crew reads either one.
            This is the goals part. Read criterion four out loud. The auditor can check it without a judgment call. That is the whole bar. Compare it with the one-sentence prompt from recording one.

            Goals

            The wargame skill writes the requirements with you.

            You do not write those files by hand. You sit in a session that interviews you and writes them. You decide the scope, and the skill decides the wording.

            phase 1Diverge

            The skill asks about users, scenarios, edge cases, constraints, and integrations. It generates candidate requirements as you talk.

            phase 2Converge

            The skill merges duplicates, points out collisions, and makes you pick. It keeps every rejected idea as excluded scope with a reason.

            phase 3Formalize

            The skill writes one requirement file per capability, sized to one crew run and ordered by dependency. Then it fills the status table.

            Keep this short. The wargame is an interview. Most of the value of this whole setup comes from this step, because the crew is only as good as the requirement it is handed.

            Plans and gates

            Four agents do four jobs. No agent does two.

            haiku

            01 · it readsScout

            The scout reads the specs, the requirement, and the code. It writes a contract that names the files to touch. It changes nothing else.

            sonnet

            02 · it writes codeCoder

            The coder implements one requirement against the coder spec. It writes no tests. It touches nothing outside the contract.

            sonnet

            03 · it writes testsTester

            The tester writes the tests against the tester spec. It maps every criterion to a named test. It touches no production code.

            sonnet

            04 · it decidesAuditor

            The auditor re-runs everything itself. It returns BLOCKED or UNBLOCKED. It is the only agent allowed to write a lesson to memory.

            scout→coder→tester→coverage gate→auditor→verdict

            The rule that matters is in the title. An agent that writes code and its own tests approves its own output. Anthropic found the same thing in their own harness work. Agents that grade themselves praise the work. So the grading stays with a separate agent.

                This is part two. Watch the file names. The coder touches the component. The tester touches the spec files. Neither one touches the other's files. If a gate condition fails, the orchestrator sends the failure back to its owner and checks again. It never sends a known failure to the auditor.

                  gate 3The verdict

                  UNBLOCKED means the work is done. BLOCKED means the run stops. A human sorts each blocker by owner, and that owner fixes it. The crew never loops on its own.

                  watch forFour things only the auditor does

                  • It runs once, after the gate, and never during iteration.
                  • It re-runs the test suite itself instead of trusting the record.
                  • It writes the audit report.
                  • It adds zero to three lessons to the memory file.
                  This is part three. The auditor checks everything again on its own. It does not trust the tester's recorded coverage. Then it writes lessons. It is the only writer to the learnings file, and that is how memory stays trustworthy.

                  End of session

                  Nothing lives in one CLI's memory.

                  At the end of a session, one skill gathers evidence from git, writes a handoff, and saves durable lessons. The next session resumes with nothing lost, on any CLI.

                  • GroundedThe skill checks every status claim against commits and files before it writes the claim. It labels anything it cannot verify as unverified.
                  • ReferencesIt records commit hashes, ticket IDs, and file and line pointers instead of prose that drifts.
                  • Next actionThe first line names the one concrete thing to do next and exactly how to do it.
                  • Any CLIThe handoff and the lessons go through the MCP server, so Claude Code, Gemini CLI, and Copilot CLI all read the same state.
                  This is a short slide. The point is that state lives in the repo and the MCP server, not in a chat history. A teammate on Gemini CLI picks up where you left off on Claude Code.
